# Perk Track

独立运行的信用卡、权益、银行开户奖励与积分账本。纯 HTML / CSS / JavaScript，没有框架、构建依赖、AI API 或第三方数据库要求。

## 开始使用

解压后双击 `Perk-Track.html` 即可试用。这是完整自包含版本，无需其他资源文件。`index.html` 是适合后续维护的分文件版本。为获得稳定的浏览器存储来源，建议部署到 GitHub Pages，或在项目目录运行：

```powershell
python -m http.server 8765 --bind 127.0.0.1
```

打开 http://127.0.0.1:8765 。初次打开显示明确标注的**虚构演示数据**；点击“开始记录我的数据”清空演示记录。切换域名、端口或浏览器会使用不同的本地存储，迁移前先导出 JSON。

## 部署到 GitHub Pages

1. 建立应用仓库，将本目录中的 `index.html`、`styles.css`、`core.js`、`github.js`、`app.js` 等文件放在仓库根目录。
2. 仓库 Settings → Pages → Deploy from a branch → `main` / `/ (root)`。
3. 打开发布地址。项目路径下的相对资源路径也能正常工作。
4. GitHub Free 通常使用公开应用仓库；个人记录不要提交到应用仓库。

## 用私有 GitHub 仓库保存数据

1. 单独建立**私有**数据仓库，例如 `perk-track-data`，勾选添加 README，以初始化分支。
2. https://github.com/settings/personal-access-tokens/new 创建 fine-grained token，仅选择此数据仓库，Repository permissions → Contents → Read and write。到期后需要更换。
3. 看板“设置”中填写用户名、仓库、`data.json` 路径和 token。分支留空可使用默认分支。
4. “保存设置并测试连接”。若文件存在，先“读取云端”；若不存在，可直接点击顶部“保存到 GitHub”创建文件。
5. 本地修改自动保存，GitHub 写入为手动操作。整理结束时保存一次即可。

token 默认放在标签页的 sessionStorage。“记住 token”会改为 localStorage；同源 JavaScript 和有相应权限的扩展可能读取它。token 永远不进入账本 JSON、CSV 或应用源码。不要在不信任的网页版本输入 token。代码没有外部字体、脚本、追踪器或第三方运行依赖。

读取云端前会要求确认，并下载当前本地备份。更新文件携带已读取文件的 SHA：另一个标签页或外部修改了文件时，GitHub 会拒绝旧版本写入。应用不自动合并、不悄悄覆盖。发生冲突先导出本地备份，再读取云端并处理差异。

网络、权限失败时保留本地修改。GitHub API 返回 404 时也可能是权限不足或分支不存在；测试成功并不保证一定有写入权限，最终以保存结果为准。

## 记账方式

v1.1 支持仅知道开户月份（`openMonth`）以及仅知道关户月份（`closeMonth`），不会补一个虚构日期。跨滚动窗口边界的月份不猜测计数；精确退窗日期仍待核对。未知额度、年费与权益额度可以留空。`capitalComplete: false` 表示本金流水不完整，此活动不参与当前本金及机会成本计算；请先补齐存取记录再勾选“本金流水完整”。`cycleConfirmed: false` 表示权益周期未知，不生成虚构截止日。

新增：每自然半年重置、未知开户日期、周期已用额度、全年已收奖励与积分余额快照。仅知使用周期时，使用流水可填 `periodStart` 和 `periodEnd`（后者是下一周期首日），不虚构使用日期或收益。仅知2026年bonus到账时，可以不填日期而填 `periodYear: 2026`，进入年度收益但不分摊月度图表。`balance` 积分事件把截至该日余额核对为指定值，不产生收入；`trackSourceBalance: false` 表示转点来源余额尚未完整录入，暂不计算来源余额。当前CL用确认日期的额度快照记录，不声称当日发生了提额。

CSP 酒店credit的官方年度边界与开户周年后的首次结单日有关，当前自动“持卡周年”模式仅是简单周年模型。请按银行显示的实际周期填“指定周期”，或保留“周期待核对”，避免提前重置。

多档SUB支持两档点数、期限和到账状态，消费进度暂为当前档字段；未知消费要求时不猜目标。服务类权益（行李/选座）按次记录使用与实际节省，不伪造周期美元额度。历史赚点/费用可仅填写年份；若某计划余额不完整，`settings.incompletePointPrograms` 可隐藏其不可靠当前余额，直到补入该计划的余额核对快照。公开标准年费与用户实付金额应核对，备注标记待核对的费用不可当作已审计净收益。

- **信用卡**：保留原始开户日；CL / 产品调整单独记事件。卡片年费字段仅为计划，真正支付后在成本账本记录。
- **SUB**：当前档目标、进度及点数；完成目标不自动生成积分。奖励到账后补一条积分事件。多档 SUB 可以在完成一档后更新目标，具体条款写进备注。
- **权益**：月、季、自然年、持卡周年、指定周期。使用额度和个人价值分开；未到账标签用于后续核对，收益依据已使用时填写的价值确认。
- **Bank churn**：DD / 存入本金增加资金余额，取出减少余额。同一笔 DD 不要再次录为存款。奖励与利息单独记录，不自动滚入本金占用；若将其留存并希望计入占用，可补存入事件。
- **银行条件**：金额、次数、存款目标、持有天数、截止、安全关户、再次申请日期。其他复杂条款保留在备注，应用不声称自动验证全部资格或连续持有要求。
- **积分**：用赚点事件补期初余额。赚点、转点不计收入；转点的实际到账点数包含已到账 bonus。未到账的奖励写进备注，到账后再更新。
- **兑换**：参考现金价格减税费 / 手续费得到兑换净价值，除以点数算 CPP。参考价格应使用真正可比、愿意购买的方案。
- **退回点数**：保留原兑换记录；退款事件记录退回点数、取消的现金参考价值（cashReference）和实际退还税费（taxes）。它恢复点数并冲回兑换收益。不要同时删除原兑换，避免重复恢复余额。若仅是非兑换原因补点，使用余额调增。
- **买点**：买点事件记录成本，在购买日期扣除；以后兑换不重复扣取得成本。
- **费用**：成本账本的费用只记一次。银行费用已记银行流水、税费已记兑换事件时，不再重复填入成本账本。费用只能归属于一张卡或一个银行活动。
- 全部金额均为 **USD，税前**。其他币种先自行换算并在备注注明汇率。

## 分类收益（v2）

主看板统计已赚奖励的当前CPP估值，而不是纯现金到账收益。分类如下：

- 银行churn：实收奖励+利息−账户费用−银行专属成本−资金机会成本。checking、savings和未拆分组合活动分别标记。
- 消费返利：实际现金返利+正常刷卡积分×CPP−归属此类的费用。按category和卡片汇总。
- Perk/报销/年费：已使用权益的个人价值+转点促销/持卡bonus估值−实付年费及其他该类成本。
- SUB：已到账SUB积分/现金价值−归属SUB的手续费、额外非必要消费损失和替代方案损失。进行中offer不计入已经赚到的收益。

每张卡同时显示三块净收益、正负项与合计；银行和信用卡合计明确分列。没有来源卡的奖励单列“未归属卡片”。飞行赚点等非信用卡收益、未分类赚点、兑换实测价值、剩余积分资产均单列，不再与已经估过值的赚点重复相加。

CPP滑块默认UR与Aeroplan各1.9¢，只是可调整的假设；拖动立即更新单卡/总体/category选卡与SUB测算。赚点估值按原始奖励币种：UR赚取本身按UR CPP估值；转点本金不产生第二笔收入，新增transfer bonus单独记perk赚点。兑票后展示实测CPP与净兑换价值用于比较，但不再往估值总收益加一次。

CFU返利通常以UR点入账（标准$200 SUB为20k UR），不能同时按现金$200和20k UR重复计。用户仅确认offer金额时，参考点数会标记估计。BoA/CFU参考SUB金额、暂按标准金额记录的年费、尚未核对到账的credit面值都不是审计后的现金收益。

## Earn category与规则

Category选卡依据可编辑rewardRules：积分倍率×CPP给出百分比，现金返利直接使用百分比。日期选择会切换有明确到期日的规则。线上超市、实体超市和网购分别比较；用户提供的超市/餐饮合计奖励不猜拆分。商户MCC、促销有效期与消费上限尚未配置/确认时，必须核对规则备注。规则比较不含SUB、不自动判断商户、不监测卡片各项额度。

## 学费与Induced consumption

本来需要交的学费本金不是额外损失。用卡付学费的增量成本可以是2.52%手续费；例如$16,000×2.52%=$403.20。追额外40k奖励且Aeroplan CPP=1.5¢时，SUB价值$600，扣手续费后SUB净额$196.80；若正常1x返利另有$240，方案总增量$436.80。这是“第一档已完成后追加16k、替代支付收益为0”的假设，不是实际已经赚到的钱。

实际支付后添加成本，选择SUB归属、学费支付手续费，填本金与比例，应用计算费用。正常刷卡返点另记消费返利。因追SUB购买本来不需要的东西，可填额外损失；另有替代方案收益时也可扣。测算本身不自动记账、不追踪用户不需要的当前累计消费。

资金机会成本仍按每日本金余额积分×年利率/365；本金流水不完整的账户不计算，不能把缺失成本理解为真实为零。全部金额为USD税前。

## 验证

需要 Node.js（测试不需安装依赖）：

```powershell
npm test
npm run check
```

测试覆盖跨月与闰日重置、开卡窗口、分段资金占用、兑换 / 转点 / 退款避免重复计收益、输入与关联验证、GitHub Unicode 文件读写、冲突和授权失败。真实 GitHub 读写需用你自己的仓库及 token 在设置页面验证。

## 文件

- `core.js`：日期、余额、权益周期、净收益与资金占用计算。
- `github.js`：GitHub Contents API，凭证与账本分离。
- `app.js`：页面、表单、本地保存、导入导出。
- `styles.css`：响应式界面，无外部资源依赖。
- `tests/`：核心计算和 GitHub API 的模拟测试。
